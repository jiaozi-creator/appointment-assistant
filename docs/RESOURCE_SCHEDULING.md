# ADR-003 · 可扩展资源排期和摄影服务套餐

状态：**在本分支实施；需浏览器/生产环境验收**。最后更新：2026-10-19。

## 为什么这么设计

原系统将每家工作室当作“同时只能接一个预约”的单一资源，不适合多人工作室。现在统一抽象为以下三个概念：

1. **资源（resources）**：摄影师、场地、设备；每个资源属于且只属于一个工作室。摄影师和场地容量为1，设备可以是同型号多份的共享库存容量（1～50）。
2. **套餐（service_packages）**：一个公开服务可有多个套餐，各有定价、时长、准备/收尾缓冲、所需资源类别及数量。例如“2人双机位写真”需要摄影师×2、影棚×1、灯组×2。
3. **分配（booking_allocations）**：只有确认后的预约占用具体资源。客服可以手工选择摄影师/影棚/设备，或者由后端自动按可用资源分配。两者均在单一数据库事务内检查冲突。

**个人摄影师不是另一套系统**：其工作室有一名 `photographer`、套餐要求摄影师×1即可；升级多人工作室只需添加资源和套餐规则。

## 模型和业务规则

- `services`：客户浏览的拍摄项目，如个人写真、毕业照。
- `service_packages`：该项目下的可预约套餐，价格以人民币 **分** 保存，时长以整数分钟保存；`is_default` 表示老服务自动生成的标准套餐。
- `package_requirements`：每种套餐要求的资源**类别**及数量；要求至少一位摄影师，场地/设备为可选。
- `bookings`：在创建时将所选套餐 ID、名称、价格、时长、前后缓冲时间记录为快照；`booking_requirements` 是套餐资源需求的快照。**套餐编辑不得影响已经提交的申请**。
- `booking_allocations`：预约具体使用哪个摄影师、场地与设备（以及库存份数）。
- `resource_blocks`：对某个资源在某一天的某个区间设置不可用。
- `resource_weekly_hours`：可选的每周工作时段。没有记录表示默认不限制；有记录时未配置的星期视为休息。API 可配置多时段，当前管理界面提供单时段快捷编辑。
- `days_off`：全店休息日，优先级高于资源的可用安排。

### 时段算法

- 工作室时区在本版固定为 `Asia/Shanghai`，全店允许的时间为 **09:00–21:00**；客户只可以半小时为粒度开始，提前1～180天预约。
- 实际占用半开区间是 `[开拍时间 - 准备缓冲, 开拍时间 + 拍摄时长 + 收尾缓冲)`。相邻边界（如 10:00 结束与 10:00 开始）不冲突。
- 限定每份资源同一瞬间的**总占用数量不得超出容量**。系统使用事件扫描计算峰值并发，避免把两个不同时段的订单简单相加造成错误拒绝。
- 封档或每周工作时间约束必须覆盖整个占用区间；新设置不能冲撞已经确认的未来预约。
- `pending` **不锁档**，允许同一时段多个预约申请；在 `pending -> confirmed` 时重新检查并在 `BEGIN IMMEDIATE` 事务里完成资源分配及状态更新。
- `confirmed -> cancelled` 会立即释放**可用容量**（历史分配记录保留以供追溯，但容量计算排除已取消订单）；`confirmed -> completed` 视作已占用历史时段。
- 若某种资源不足，返回 HTTP `409` 并保留原预约状态。跨工作室资源 ID 必须拒绝。

### 资源选取策略

自动分配按 `kind,name,id` 稳定顺序先找到满足套餐资源数量的资源，可能不是业务上最偏好的摄影师；后台可手动选择。**当前没有摄影师技能标签、客户偏好/指派规则、资源联合最优求解或跨日订单**。

### 示例

- 独立摄影师：小李×1，独立写真标准套餐：`photographer:1`，90分钟拍摄 + 前后各15分钟。
- 多人工作室：小李×1、小王×1；A棚×1、B棚×1；柔光灯库存×2。套餐要求摄影师×1、影棚×1、灯组×1，10:00 可以确认两笔不冲突的订单，但无法确认第三笔。
- 团队套餐：摄影师×2、影棚×1、灯组×2，需同时获得足额资源；不会因摄影师空闲就忽略设备短缺。

## 重要风险与下一阶段

1. **数据库仍是SQLite**：当前只适合单部署节点、受控小规模试点。写操作的互斥依赖 `BEGIN IMMEDIATE`；未来升级PostgreSQL时必须重做事务锁与容量约束（事务中的资源锁或 advisory locks），不能仅迁移DDL。
2. **并发并非支付占位**：客户看到“可选时段”仅为当时计算结果，提交后待商家确认；无临时锁档、定金和超时释放。
3. **跨天、时区、夏令时不支持**：中国境内试点外需要添加 `merchants.time_zone` 并统一转换日期与绝对时刻。
4. **设备数量是假设同质库存**：单件相机序列号、维修折旧、跨店调拨、资源分组与嵌套依赖尚未开发。
5. 受控试点前需完成浏览器端E2E、迁移备份/回滚演练、实际并发压测、日志审计和隐私合规审查。

## API 摘要

| 方法 | 资源路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/public/shops/:slug/packages?service_id=` | 公开 | 查看上架套餐与数量规则 |
| GET | `/api/public/shops/:slug/availability?date=&service_id=&package_id=` | 公开 | 当前套餐可用起始时段，不含人员姓名或联系方式 |
| POST | `/api/public/shops/:slug/bookings` | 公开、频率限制 | 额外接收 `package_id`，创建快照，不占用资源 |
| GET/POST | `/api/admin/resources` | 商家成员读取/老板写入 | 资源台账 |
| PATCH | `/api/admin/resources/:id` | 老板 | 修改名称、容量、启停（不得破坏已确认预约） |
| GET/POST | `/api/admin/resource-blocks` | 成员读取/老板写入 | 临时封档 |
| DELETE | `/api/admin/resource-blocks/:id` | 老板 | 解除封档 |
| GET/PUT | `/api/admin/resources/:id/weekly-hours` | 成员读取/老板写入 | 每周时段 |
| GET/POST | `/api/admin/packages` | 成员读取/老板写入 | 配置套餐 |
| PATCH/DELETE | `/api/admin/packages/:id` | 老板 | 编辑或下架（保留历史订单快照） |
| GET | `/api/admin/resource-calendar?date=` | 成员 | 已确认资源占用与封档列表 |
| GET | `/api/admin/bookings/:id/resource-needs` | 成员 | 当前预约的资源需求快照及可分配资源 |
| PATCH | `/api/admin/bookings/:id/status` | 成员 | `confirmed` 时可传 `allocations: [{resource_id,quantity}]`，不传则自动分配 |

后台对资源相关写操作仍强制会话、CSRF 和工作室权限校验。
